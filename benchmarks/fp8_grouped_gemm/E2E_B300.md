# FP8 cleanup end to end on B300: no speedup

On 8x8 B300, full-depth DSv4 Flash SFT runs at the same speed before and after this branch: 17.323 s/step
before, 17.336 s after. Both are 2.7% slower than bf16 (16.874 s). On H200 the same changes took a 6-layer
model from 8.43 s to 7.13 s per forward+backward, level with bf16. This note records both results and the
differences between the two setups, as a starting point for finding out why the H200 gain does not show up.

## B300 setup

- Configs: `sft.toml` (bf16) and the `sft_fp8.toml` overlay in this directory. 8 nodes, 64 B300 (SM100),
  `PrimeIntellect/DeepSeek-V4-Flash-0731-bf16` at all 43 layers, `seq_len` 262144, `cp` 8, `ep` 8,
  `batch_size` 8 (one micro-step per rank, 32768 tokens per GPU), AdamW, constant LR, torch MoE dispatch.
- Selective activation checkpointing with the #3643 targets; no activation or optimizer offload.
- Fake data (`input_ids = "random"`, fixed length) with `model.debug.force_balanced_routing = true`, 20 steps.
- The FP8 overlay turns on both dense FP8 linears (`model.quantization`, 301 linears replaced) and the
  DeepGEMM FP8 grouped GEMM for all 43 MoE layers. Its ignore list is the one from #3627, which adds
  `o_a_proj` (the dense rewrite breaks `DeepseekV4GroupedLinear` on main), `indexer\.` and `compressor\.`.
- Both FP8 arms use the identical config. "before" is `main` at `33e02a7a1`; "after" is this branch rebased
  onto that commit (code at `50b09e508`). bf16 ran from this branch; this branch leaves the bf16 path alone.

Launch, from the worktree whose code is under test:

```
uv run sft @ benchmarks/fp8_grouped_gemm/sft.toml @ benchmarks/fp8_grouped_gemm/sft_fp8.toml --run.name <name>
```

checkpointing, median `time/forward_backward` over steps 3-15:

| Code | bf16 | fp8 |
|---|---|---|
| base `ae37b35a3` | 7.16 s | 8.43 s |
| + weight grad in parameter layout (`5daa36725`) | 7.16 s | 7.19 s |
| + 128-row groups, host syncs 5 to 1 (`520b9de39`) | 7.16 s | 7.13 s |

At the op level on H200, at 32768 tokens per GPU (the same tokens per GPU as the B300 runs), fp8 fwd+bwd

## The gap to explain

On H200 the branch saved 1.30 s across 6 MoE layers, about 0.2 s per layer. At that rate the B300 run's 43
layers would save several seconds per step; the measured saving is zero. The op-level saving (about 7.6 ms
per layer per fwd+bwd) predicts only about 0.3 s for 43 layers, so even the H200 end-to-end gain was larger
than its op-level cause, which suggests host stalls rather than GPU work.

Differences between the two setups, any of which could account for it:

- GPU: SM100 takes different code paths in `fp8_grouped_gemm.py`. The wgrad uses
  `k_grouped_fp8_gemm_tn_contiguous` with row-major per-channel casts instead of the SM90 k-major path, and
  scales are UE8M0. The AccumulateGrad copy that `5daa36725` removed may not exist or may be cheap on SM100.
- Host stalls: the H200 gain is consistent with removing syncs that stalled the host. If the B300 step is
  GPU-bound (larger model, CP communication, SAC recompute), the host may already be far enough ahead that
  syncs cost nothing.
- Shape: 43 layers at `cp` 8 with 256k sequences instead of 6 layers at `cp` 1 with 32k. Attention's share of
  the step is far larger at 256k, which dilutes any MoE change.
- Checkpointing: selective instead of full. The #3643 target list replaces the defaults and names only the
  sparse attention, the equal-split all-to-all and the stable sort, so the grouped GEMMs are recomputed in
  backward as under full checkpointing, while attention is not.
- Routing: forced balanced routing gives every local expert `32768 * 8 * 6 / 256 = 6144` rows, a multiple of
  128. The old alignment-8 path then needed no padding, and its unpack copies moved every row to where it
  already was (still paid for). The H200 end-to-end runs used learned routing on real weights.
- Dense FP8: both B300 FP8 arms also quantize 301 dense linears, which the branch does not change; this adds
  equal cost to both arms and explains part of the gap to bf16, but not the missing before/after difference.

## Suggested next measurements

- Profile one steady-state step of each FP8 arm on B300 (`trace_path`) and compare MoE grouped GEMM time,
  cast time, AccumulateGrad copies and host-side gaps before the syncs.
- Rerun the H200 shape on B300 (6 layers via `model.debug.num_layers`, 32k, `cp` 1, full AC) to separate
  the GPU from the shape.
- Run the op-level harness (`bench.py`) on one B300 for base and branch.
- Repeat the B300 A/B with MoE FP8 only (drop `model.quantization`) and with learned routing
  (`force_balanced_routing = false`) to rule out the dense linears and the balanced group sizes.
